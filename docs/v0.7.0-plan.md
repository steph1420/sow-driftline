# v0.7.0-beta.1 build plan

Steve said GO at t88u. This is a Beta-only build on the test copy. The spec is `FEATURES.md` together with the locked mocks in `docs/mockups/`.

## Rules for every step
- The failing test comes first; each step is a small commit authored by LFPS~SOW, with files added by explicit path.
- Each step is a self-check of under 3 minutes. If the same error happens twice, stop.
- The backup is the `backup/pre-v0.7.0` branch plus `/workspace/backup-sow-driftline-pre-v0.7.0.tgz` on the box.
- A release counts as done only when Actions is green and the `/sow-driftline-beta/` bundle hash has changed. Rollback means setting BETA_REF back to `v0.6.0-beta.1`.

## How every step runs (the gate)
1. **Scope.** The step lists the files it may touch, and it touches nothing else. If another file needs changing, stop and add that change to a later step. No refactors and no drive-by fixes; bugs found along the way go into `BUGS.md`.
2. **Test first.** Write the failing test for the step's behaviour and commit it with the step.
3. **Build.** Make the change.
4. **Gate.** Before any commit, all of these must pass:
   - `vitest` all green, so every earlier step still works;
   - `tsc -b` clean;
   - `vite build` OK;
   - a demo-data screenshot in phone night and day, checked against the locked mock.
5. **Commit.** One commit per step, `v0.7.0 Sn: …`, adding files by explicit path and pushing `feat/v0.7.0`. Steps are tagged `v0.7.0-sN` so any step can be rolled back on its own.
6. **Steve.** Send him one screenshot per step. Steps that change data (S6, S7, S8) wait for his OK before the next step starts.
7. **Stop rules.** If the same error happens twice, stop and report. Nothing deploys until S11. The live sheet is never touched.

The steps are ordered from the safest (looks only) to the riskiest (writes data), so the early steps can't break saving.

## Bridge (test copy)
The deployed copy bridge supports `push` with tick ops and `structs` of kind `rename` and `delete`. That covers moving a date (S6).

These need a **bridge update on the test copy**, which Steve has to deploy because Apps Script can't be deployed from the box:
1. **Save topic** for an existing session. Proposed: a struct `{kind:'topic', subjectKey, date, topic}`.
2. **New date with no ticks yet.** Today a session only appears on the sheet with its first tick, and that push already carries the topic. Proposed: a struct `{kind:'add', subjectKey, date, topic}`.
3. **Back-date `markedOn`** shared across devices. Proposed: a new Ticks column K, `markedOn`, written only when a tick is back-dated.

**Plan:**
- Write bridge `0.51.0-dl.1` (purely additive) with bridge tests in `bridge/test/`.
- Until Steve deploys it, the app keeps these three things **on the device** (`storageKey('marks')` and pending structs), shown normally and sent when the bridge reports version 0.51 or later.
- Demo mode works fully with no bridge.
- The live sheet is never touched.
